mogenius exposes its own **Model Context Protocol (MCP) server**, so external AI‑powered tools — such as IDE assistants, Claude, or custom automations — can interact with your Kubernetes cluster through the same AI infrastructure that powers [Agents](/ai/agents) and [Chat](/ai/chat).

The server is reachable at:

```
https://platform-api.mogenius.com/mcp
```

<Note>
This is the **outbound** direction: external clients connect **to** mogenius. To connect external tools **to your agents** (for example a GitHub or GitLab MCP server), see [Tools & Custom MCP Servers](/ai/tools#custom-mcp-servers) instead.
</Note>

## Authentication

The mogenius MCP server supports two ways to authenticate. Pick the one your client supports:

- **OAuth (recommended)** — for clients that support remote MCP servers with sign‑in, such as Claude and Cursor. You add the server URL, a browser opens, you sign in to mogenius and approve access. No key to copy or store.
- **API key** — for clients that can only send a static `Authorization` header. You create a key in mogenius and paste it into the client's config.

Both methods respect your mogenius permissions: a client can only see and act on the namespaces and resources your login (or the API key owner) is allowed to.

### OAuth sign‑in and consent

When a client connects with OAuth, mogenius opens a **consent screen** in your browser. You choose:

- the **organization** the session acts in,
- the **role** it uses (for example viewer or editor), and
- optionally, a single **cluster or workspace** to restrict the session to.

The resulting access is **scoped to the MCP server only** — the token cannot be used against the rest of the mogenius REST API. You can review and revoke every connected client at any time under **Profile → Devices**.

Discovery is automatic: the client finds the mogenius authorization server from the `/mcp` endpoint (per the OAuth protected‑resource standard), registers itself, and runs the sign‑in flow. You only ever provide the server URL.

### API keys

An API key is a single opaque token that starts with `mo_pat:`. A key is **always a personal key** — it is tied to your user account and inherits your permissions. When you create it, you set its **scope** to an organization, a cluster, or a workspace, so the same personal key can be narrowed to exactly the resources a client needs.

You can:

- create several keys, each with its own scope,
- revoke a key at any time from the platform settings.

Create and manage API keys in your **Profile → API Keys**.

## Connecting a client

### Claude

Claude connects to remote MCP servers as a **custom connector** and signs in with OAuth — no API key required.

1. Open **Settings → Connectors → Add custom connector**.
2. Enter the mogenius MCP server URL: `https://platform-api.mogenius.com/mcp`
3. Complete the mogenius sign‑in and consent in the browser window that opens.

For Claude Code, add it from the terminal:

```bash
claude mcp add --transport http mogenius https://platform-api.mogenius.com/mcp
```

The first request triggers the browser sign‑in automatically.

<Tip>
If your client does not yet support OAuth for remote MCP servers, use `mcp-remote` with an API key as shown below.
</Tip>

### Cursor

In the Cursor Desktop app, open **Settings → Tools & MCP** and add a new MCP server. Cursor opens your `mcp.json` — add the mogenius server with its URL and let Cursor run the OAuth sign‑in:

```json
{
  "mcpServers": {
    "mogenius": {
      "type": "streamable-http",
      "url": "https://platform-api.mogenius.com/mcp"
    }
  }
}
```

To authenticate with an API key instead of OAuth, add the header:

```json
{
  "mcpServers": {
    "mogenius": {
      "type": "streamable-http",
      "url": "https://platform-api.mogenius.com/mcp",
      "headers": {
        "Authorization": "bearer YOUR-MOGENIUS-API-KEY"
      }
    }
  }
}
```

### API key via `mcp-remote`

For clients that only support local (stdio) MCP servers, bridge to the remote server with `mcp-remote` and authenticate with an API key. Adapt the following and add it to the client's MCP config (for example `claude_desktop_config.json`):

```json
"mcpServers": {
    "mogenius": {
      "command": "PATH-TO-YOUR-NODE-INSTALLATION/.nvm/versions/node/v23.3.0/bin/npx",
      "args": [
        "-y",
        "mcp-remote",
        "https://platform-api.mogenius.com/mcp",
        "--header",
        "Authorization: bearer YOUR-MOGENIUS-API-KEY"
      ],
      "env": {
        "PATH": "PATH-TO-YOUR-NODE-INSTALLATION/.nvm/versions/node/v23.3.0/bin:/usr/local/bin:/opt/homebrew/bin:/usr/bin:/bin"
      }
    }
  }
```

## Tools & capabilities

The mogenius MCP server exposes the same tools available to agents and chat, so external clients can perform cluster operations through natural language or structured requests.

### Kubernetes

- List and describe Pods, Deployments, Services, ConfigMaps, and other resources.
- Read Pod logs and events for troubleshooting.
- Retrieve resource manifests and status information.
- Inspect namespace‑level overviews.
- Create and modify resources and workloads.

### Helm

- List installed Helm releases across namespaces.
- Inspect chart values and release configuration.
- Review release history and rollback information.
- Deploy Helm charts.

## Auditing MCP activity

Requests made through the mogenius MCP server are recorded in the cluster [audit log](/cluster-management/audit-log) and tagged as MCP requests, so you can trace which actions were taken by external clients.
