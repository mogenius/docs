The mogenius platform is available as a SaaS option on [app.mogenius.com](https://app.mogenius.com). If you prefer the self-hosted version of mogenius, you can install it with our Helm chart. This way you can run mogenius on your own clusters and even in air-gapped environments.

## Prerequisites
- A Kubernetes cluster with at least 1 CPU and 1 GB of memory available.
- Credentials for pulling the mogenius images from the container registry (see below).
- The traefik ingress controller.
- A working local installation of [Helm](https://helm.sh/).
- A MySQL server (optional).

<Warning>
  Running the platform as a self-hosted version requires a subscription. <a href="mailto:sales@mogenius.com">Contact our sales team</a> for more information.
</Warning>

## Quickstart
For a quick installation of the mogenius platform with defaults where possible, follow these steps.

### Create a Namespace
On the cluster where you're installing the mogenius platform, create a new namespace `mogenius-platform`. All following commands target this namespace.

```bash
kubectl create namespace mogenius-platform
```

### Create Secrets

The platform services require a few secrets containing critical credentials that aren't created by the Helm chart. The following secrets are required for the minimum configuration. Additional secrets can be used when working with more sophisticated Helm chart configurations.

The commands below create each secret directly with `kubectl`. They generate secure random values on the fly using `openssl`, so you can run them as-is and only replace the placeholders that are marked with `<...>`.

<Note>
  The encryption key `MO_CORE_NEST__SSH_SYM_ENC_KEY` must be **identical** in the `mo-platform-shared` and `mo-platform-user-secret` secrets. The commands below generate it once into a shell variable and reuse it, so run them in the same terminal session.
</Note>

**1. Container Registry**

After obtaining a subscription for the self-hosted version, you will have received credentials for the container registry where the platform images are stored. Store them as a `mo-registry-credentials` secret of type `kubernetes.io/dockerconfigjson`. Replace the placeholders with the values from your subscription.

```bash
kubectl create secret docker-registry mo-registry-credentials \
  --namespace mogenius-platform \
  --docker-server=<REGISTRY_SERVER> \
  --docker-username=<REGISTRY_USERNAME> \
  --docker-password=<REGISTRY_PASSWORD>
```

**2. Valkey (Redis-compatible)**

Holds the password shared by all Valkey instances. The command generates a secure random value.

```bash
kubectl create secret generic mo-redis-secret \
  --namespace mogenius-platform \
  --from-literal=REDIS_SECRET="$(openssl rand -base64 32)"
```

**3. Encryption Key**

Generate the symmetric encryption key once and keep it in a shell variable so it can be reused for the admin user secret in step 5.

```bash
export MO_ENC_KEY="$(openssl rand -base64 32)"

kubectl create secret generic mo-platform-shared \
  --namespace mogenius-platform \
  --from-literal=MO_CORE_NEST__SSH_SYM_ENC_KEY="$MO_ENC_KEY"
```

**4. MySQL**

Holds the application and root passwords for the MySQL database. The command generates secure random values.

<Warning>
  Avoid single quotes (`'`) and backslashes (`\`) in MySQL passwords — they break the MySQL container's init and cause *Access denied*. Use **alphanumeric passwords** (`A–Z`, `a–z`, `0–9`). The command below already generates compliant values.
</Warning>

```bash
kubectl create secret generic mo-mysql-secret \
  --namespace mogenius-platform \
  --from-literal=MYSQL_PASSWORD="$(LC_ALL=C tr -dc 'A-Za-z0-9' </dev/urandom | head -c 32)" \
  --from-literal=MYSQL_ROOT_PASSWORD="$(LC_ALL=C tr -dc 'A-Za-z0-9' </dev/urandom | head -c 32)"
```

**5. Admin User**

Holds the credentials for the initial admin user and the OAuth signing secrets. First generate the JWKS used for signing JWTs and the random secrets used for cookie signing and the BFF OAuth client:

```bash
export MO_OAUTH_JWKS="$(node -e "const k = require('crypto').generateKeyPairSync('ec', { namedCurve: 'P-256' }).privateKey.export({ format: 'jwk' }); console.log(Buffer.from(JSON.stringify({ ...k, alg: 'ES256' })).toString('base64'))")"
export MO_OAUTH_COOKIE_KEYS="$(node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))")"
export MO_OAUTH_BFF_CLIENT_SECRET="$(node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))")"
```

Then create the secret. Replace the admin email and password placeholders; all other values are derived automatically (`MO_CORE_NEST__SSH_SYM_ENC_KEY` reuses the `$MO_ENC_KEY` from step 3).

```bash
kubectl create secret generic mo-platform-user-secret \
  --namespace mogenius-platform \
  --from-literal=MO_USER_NEST__SYSTEM_ADMIN_EMAIL="<ADMIN_EMAIL>" \
  --from-literal=MO_USER_NEST__SYSTEM_ADMIN_PASSWORD="<ADMIN_PASSWORD>" \
  --from-literal=MO_CORE_NEST__SSH_SYM_ENC_KEY="$MO_ENC_KEY" \
  --from-literal=MO_USER_NEST__OAUTH__JWKS="$MO_OAUTH_JWKS" \
  --from-literal=MO_USER_NEST__OAUTH__COOKIE_KEYS="$MO_OAUTH_COOKIE_KEYS" \
  --from-literal=MO_USER_NEST__OAUTH__BFF_CLIENT_SECRET="$MO_OAUTH_BFF_CLIENT_SECRET"
```

The keys stored in this secret are:

`MO_USER_NEST__SYSTEM_ADMIN_EMAIL` — the email address to log in with your admin user.
`MO_USER_NEST__SYSTEM_ADMIN_PASSWORD` — the password for your admin user.
`MO_CORE_NEST__SSH_SYM_ENC_KEY` — the same encryption key set in the `mo-platform-shared` secret.
`MO_USER_NEST__OAUTH__JWKS` — the base64-encoded JWK (P-256, ES256) used for signing and verifying JWTs.
`MO_USER_NEST__OAUTH__COOKIE_KEYS` — a secure random secret for signing session cookies.
`MO_USER_NEST__OAUTH__BFF_CLIENT_SECRET` — a secure random client secret for the backend-for-frontend OAuth client.


### Prepare your values.yaml
The Helm chart supports wide range of values that you can use to configure your installation of the mogenius platform. Skip to [values](/cluster-management/self-hosted#values) for a full reference of the chart.
Below is an example `values.yaml` for a minimal setup to install the mogenius platform in a development environment. Make sure to review the configuration and ensure that it matches your infrastructure.

```yaml values.yaml quickstart example 
ingress:
  ingressClassName: traefik
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt-cluster-issuer
    traefik.ingress.kubernetes.io/forward-headers: "true"
    traefik.ingress.kubernetes.io/router.middlewares: mogenius-platform-cors-middleware@kubernetescrd
    traefik.ingress.kubernetes.io/secure-headers: "true"
  api_service_url: platform-api.YOURDOMAIN.com
  hostname: mogenius.YOURDOMAIN.com
  k8s_cmd_stream_url: k8s-cmd-stream.YOURDOMAIN.com
  k8s_dispatcher_url: k8s-dispatcher.YOURDOMAIN.com
  k8s_logs_url: k8s-logs.YOURDOMAIN.com
  k8s_websocket_url: k8s-ws.YOURDOMAIN.com
  rootDomain: YOURDOMAIN.com
  socket_service_url: platform-ws.YOURDOMAIN.com
  user_service_url: platform-user.YOURDOMAIN.com
  tls:
  - hosts:
    - mogenius.YOURDOMAIN.com
    - platform-api.YOURDOMAIN.com
    - platform-user.YOURDOMAIN.com
    - platform-ws.YOURDOMAIN.com
    - k8s-ws.YOURDOMAIN.com
    - k8s-logs.YOURDOMAIN.com
    - k8s-cmd-stream.YOURDOMAIN.com
    - k8s-dispatcher.YOURDOMAIN.com
    secretName: mo-platform-tls
  traefik:
    apiVersion: traefik.io/v1alpha1
mo_platform:
  metrics:
    enabled: true
    serviceMonitor:
      enabled: true 
    resources:
      requests:
        cpu: 10m
        memory: 50Mi
mo_platform_api:
  enableAutoRefreshToken: true
  refreshTokenTask: true
  openid:
    enabled: false
mogenius:
  imagePullSecrets:
  - mo-registry-credentials
mysql:
  enabled: true
  ssl: false
storage:
  accessMode: ReadWriteOnce
  className: local-path
```

<Warning>
  This chart configuration deploys the MySQL Docker image as part of the platform deployment. This setup is not recommended for running the mogenius platform in production scenarios. We recommend configuring the `mysql` values with connection to a high-availability MySQL for use in a production environment.
</Warning>

### Deploy the Helm chart
Run the following command on your cluster to install the Helm chart with your values.yaml.

```bash
helm repo add mogenius-private https://helm.mogenius.com/private
helm install mogenius-platform mogenius-private/mo-infrastructure -n mogenius-platform -f values.yaml
```

### Access the mogenius web interface
Check the status of the installation and make sure all Pods are starting properly.

```bash
kubectl get pods -n mogenius-platform
```

When all Pods are `Running`, access the mogenius platform with the hostname you specified in your Ingress (e.g. mogenius.yourdomain.com). You can log in with the credentials of your admin user.

<Accordion title="Migrating from v7 to v8: JWT/session secrets replaced with OAuth JWKS-based secrets" icon="key">
  In v8, the `MO_USER_NEST__JWT_PRIVATE`, `MO_USER_NEST__JWT_PUBLIC`, and `MO_USER_NEST__SESSION_SECRET` keys in the `mo-platform-user-secret` secret are discontinued. They're replaced by three new keys: `MO_USER_NEST__OAUTH__JWKS`, `MO_USER_NEST__OAUTH__COOKIE_KEYS`, and `MO_USER_NEST__OAUTH__BFF_CLIENT_SECRET`. The chart also drops the token lifetime settings under `mo_platform_api.openid`. If you're upgrading from v7, update your secret and `values.yaml` as follows:

  1. **Generate the new secret values:**

  ```bash
  # MO_USER_NEST__OAUTH__JWKS (one line of base64; decode with `base64 -d` to inspect the JWK)
  node -e "const k = require('crypto').generateKeyPairSync('ec', { namedCurve: 'P-256' }).privateKey.export({ format: 'jwk' }); console.log(Buffer.from(JSON.stringify({ ...k, alg: 'ES256' })).toString('base64'))"

  # MO_USER_NEST__OAUTH__COOKIE_KEYS and MO_USER_NEST__OAUTH__BFF_CLIENT_SECRET (run once per value)
  node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"
  ```

  2. **Update the `mo-platform-user-secret` secret** — remove `MO_USER_NEST__JWT_PRIVATE`, `MO_USER_NEST__JWT_PUBLIC`, and `MO_USER_NEST__SESSION_SECRET`, and add the three generated values as `MO_USER_NEST__OAUTH__JWKS`, `MO_USER_NEST__OAUTH__COOKIE_KEYS`, and `MO_USER_NEST__OAUTH__BFF_CLIENT_SECRET`. See [Create Secrets](#create-secrets) for the full `kubectl create secret` command — rerun it (or `kubectl delete secret` first) with the new keys.

  3. **Remove the deprecated token lifetime settings** from `mo_platform_api.openid` in your `values.yaml` — they're no longer valid chart values:

  ```yaml values.yaml (v7, deprecated)
  mo_platform_api:
    openid:
      accessTokenLifetime: "600"
      refreshTokenLifetime: "7776000"
      adminAccessTokenLifetime: "28800"
  ```

  4. **Run `helm upgrade`** with your updated `values.yaml` against the new chart version.

  <Note>
    All other v7 values and secrets (MySQL, Valkey, encryption key, admin credentials) remain unchanged. Only the JWT/session keys in `mo-platform-user-secret` and the `openid` token lifetime settings are affected by this migration.
  </Note>
</Accordion>

<Accordion title="Migrating from v5 to v7: OpenID moved from the user service to the API service" icon="arrow-up-right-dots">
  In v7, the user service (`mo_platform_user`) and its dedicated Valkey instance (`mo_user_valkey`) are discontinued and removed from the chart. OpenID/SSO configuration moves to the API service (`mo_platform_api`). If you're upgrading from v5, update your `values.yaml` as follows:

  <Warning>
    The `mo_platform_user` and `mo_user_valkey` keys no longer exist in the v6 chart schema. If either is still present in your `values.yaml` — even just `mo_platform_user.enabled: false` — Helm chart rendering will fail. Remove both blocks entirely rather than disabling them.
  </Warning>

  1. **Move your OpenID config** from `mo_platform_user.openid.*` to `mo_platform_api.openid.*`:

  ```yaml values.yaml (v5, deprecated)
  mo_platform_user:
    openid:
      enabled: true
      provider:
        github:
          enabled: true
  ```

  ```yaml values.yaml (v6)
  mo_platform_api:
    openid:
      enabled: true
      provider:
        github:
          enabled: true
  ```

  2. **Delete the `mo_platform_user` and `mo_user_valkey` blocks** entirely from your `values.yaml` — they're no longer valid chart values.

  3. **Run `helm upgrade`** with your updated `values.yaml` against the new chart version.

  <Note>
    All other v5 values (secrets, MySQL, remaining Valkey instances) remain unchanged. Only the `openid` block, the user service and its Valkey instance are affected by this migration.
  </Note>
</Accordion>
